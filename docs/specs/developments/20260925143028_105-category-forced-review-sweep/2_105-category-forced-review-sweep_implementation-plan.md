## Summary

**Approach**: Ship the recorded category list as a committed JSON artifact (`docs/testing/ronda/sweep-categories.json`, version `sweep-categories-v1`) read by the pass. Sweep enablement rides the existing operator-configuration precedence as a new `RONDA_SWEEP_MODE` key (same on/off/1/0/true/false vocabulary as durability mode, plus an explicit `default` alias for `off`). When enabled and the list is valid, `run-review-pass` appends a category sweep section to the review prompt, records per-category outcomes on the check-run output and logs, and stamps the review summary with the activation and list version; every degraded path (off, unrecognized value, unreadable/empty/malformed list) degrades to the existing non-sweep review with the spec-mandated record and no failure. The benchmark fixture gains five seeds (four unseeded real themes plus one harder credential-pattern case), and a committed evidence document under `docs/testing/ronda/` records the sweep-off/sweep-on recall, variance, precision, and cost comparison.

**Estimated complexity**: L

**Rationale**: The sweep itself is small (config key, one prompt section, two summary renderers, per-category record in `run-review-pass` with terminal-failure bookkeeping — AC1's surfaced rule), but the item's bulk is evidence: five fixture seeds with recorded rule metadata (AC12, AC13), a ≥5-sample × 2-configuration benchmark campaign including an original-fixture control (AC8), paired precision runs (AC9), paired cost metrics (AC11), and the adjudication-outcome, terminal-miss-record, and evidence-tier bookkeeping model (AC15). One review pipeline change plus a multi-day measurement campaign and several new committed evidence artifacts.

**Dependencies**: None blocking. The spec names #24 (seeded benchmark suite — merged, fixture exists) and #53 (capture-external-review-misses — merged, comparison records exist) as evidence lineage, not as merge-order dependencies; both surfaces are already on `develop`. If either surface is not present on `develop` when implementation begins — #24's `tests/fixtures/recall-benchmark/manifest.json` and `patches.json`, or #53's committed comparison/miss records — the plan does not silently substitute: step 10's pre-extension snapshot (the original-thirteen control) requires #24's fixture files to exist before it can copy them, so a missing #24 fixture **stops implementation at step 10** and the missing surface is raised rather than a fixture being reconstructed from memory; and the evidence campaign (steps 12/13), which reads #53's adjudication and miss records for AC15/AC16, records those records' absence as the reason its evidence is incomplete rather than fabricating the lineage. Both are stated here because the plan's steps assume the lineage exists; a reader re-validating this plan later must be able to tell that the assumption is checkable at step 10, not implicit.

- [ ] `src/core/run-review-pass.ts` — the pass orchestration change, after the draft and existing-check-run skip gates (so pre-review skips never read the list, never emit sweep metadata — AC1) and after the config/credential failure gates:
  1. Resolve enablement from `deps.config.sweepMode`/`sweepModeRaw`. If off and the raw value was non-empty unrecognized, compute the record — but **hold it pending and emit nothing yet**. The boundary is not the changed-files read: AC1 defines review execution as reading the changed files **and** running the review, and its terminal-failure rule draws the line at the review request the pass issued, so a pass that dies between the two — an authoritative-document fetch or any other GitHub error raised after `readChangedFiles` and before `deps.model.complete` — reached nothing and owes no sweep record at all, not even a degraded one; emitting at the read would report a sweep consideration for a pass the spec says is indistinguishable from the same failure without the sweep. So the record is emitted only once the pass issues its review request: then log an `sweep_enablement_unrecognized` event (no raw value in the message — fields carry `true` only) **and** carry the unrecognized-enablement `SweepDegradedRecord` into `buildCheckRunOutput` on the success path. The spec puts this record on the surfaces AC1 assigns (AC18), so a completing pass that publishes a review carries it in the check-run output as well as the logs; the review body never carries it (AC3's statement belongs only to a sweep pass that publishes).
  2. If on, load and validate the category list through `(deps.loadSweepList ?? loadSweepList)()` — the injected-loader seam named in the `sweep-categories.ts` entry, which is how a pass-level test reaches each malformed shape without touching the committed artifact. Invalid (unreadable, empty, malformed per AC19): **compute the degraded record and hold it pending, exactly as step 1 does for the unrecognized-enablement record** — the invalid-list path is not exempt from AC1's boundary, so a pass that dies between the failed list load and the review request (the authoritative-document fetch above all) emits nothing, not even `sweep-did-not-run`. Then proceed as an ordinary non-sweep review and, once the pass issues its review request, emit: log `sweep-did-not-run` with the reason and carry the invalid-list `SweepDegradedRecord` into `buildCheckRunOutput` on the success path, so the successful review-outcome check run states the degradation and reports no list version — the pass never fails and never loses publication eligibility. **AC19, AC2, AC1**
   The record name is the spec's (`sweep-did-not-run`, hyphenated) and this plan uses it verbatim; it is the one event name in this change that is hyphenated rather than the repo's snake_case convention, so do not "correct" it to `sweep_did_not_run`.
  3. If on and valid: pass `sweepCategories` into `buildReviewPrompt`; mark every category in the request as "reached" (AC1's rule — reached = carried by the one request the pass issued); after the model response is parsed, classify with a new pure function `classifyFindings` (in `src/review/sweep-categories.ts`) that is a function of the parsed findings and the recorded list alone — no regex, no stemming, no model call. Rule: normalize each finding to lowercase `title + "\n" + body`. A finding matches a category when the normalized text contains **any of that category's recorded `matchTerms`** as a literal substring — the only signal, drawn from the category's `failureShape` wording, which is the same wording the prompt section shows the model, so a finding that genuinely belongs to a category carries the vocabulary the classifier reads without the model being asked to name an identifier (see the `review-prompt.ts` entry above for why that carrier holds — the `matchTerms` come from the wording the prompt section itself renders — and for the vocabulary-divergence case: a category finding phrased without its `matchTerms` is recorded uncategorized with that category `produced_none`, asserted in scenario 2, and no fourth outcome is added because AC1 fixes the three-outcome vocabulary). The category `identifier` is prompt-side vocabulary the model reasons with and is **not** a classification signal here: matching on it would require the model to write sweep vocabulary into the finding's `title`/`body` — the published review body — which AC1 forbids. A finding matching one or more categories is recorded against every category it matches (AC20's "one or more"); a finding matching none increments `uncategorizedFindingCount`. Each category with at least one match is `produced_findings`; each with none is `produced_none`. Alongside the outcomes, `classifyFindings` emits one attribution entry per parsed finding — the finding's publication index (its position in the parsed response's findings array, the same order the review body publishes in) and the identifier list of the categories it matched, empty when it matched none — so each finding is individually attributable, not merely counted, **without carrying the finding's own text: the entry is what the `sweep_pass_record` log line renders, and a model-generated `title` there would put reviewed content on a log surface under redaction rules that only cover recognized sensitive literals (spec L1013–1014, "non-sensitive counts"). ### Parser-risk addendum

This plan **is parser-risk**, and the classification is not the whole file: most of it (the config parser, the list validator, the prompt section, the renderers) is field validation and record-keeping over structured values. It is parser-risk because of **scenario 7's credential scan** (plan step 10, AC14): a named scan function walks committed markdown, JSON, and TypeScript fixture/evidence text and classifies arbitrary text against a set of credential shapes — `sk-…`, `ghp_…`, `ghs_…`, a JWT three-dot form, a `Bearer <token>` authorization value, and any `authorization`/`token`/`password`/`secret`/`api[_-]?key`-named field carrying a non-placeholder value. That is "explicit behavior described as regex-heavy scanning … over markdown, code, config, or logs" — the protocol's own third classification signal — so the block applies and the edge-case enumeration below is mandatory, not optional.

The same classification reaches `classifyFindings` (rule 3), which matches each category's `matchTerms` as case-insensitive literal substrings against finding text. That half is deliberately **not** regex-driven — literal substring containment, no patterns — so it needs no boundary-variant set; it is covered by the ordinary unit cases in the Testing Strategy's scenario 2 (one match, two matches, no match, case-insensitivity, determinism, and the vocabulary-divergence case — a category finding written without its `matchTerms` is recorded uncategorized with that category `produced_none`, which is the classifier's honest lexical limit and stays inside the fixed three-outcome vocabulary).

#### Edge-case enumeration (scenario 7's scan)

**Verification method, stated once**: each case below is a row of the scan's own named function, exercised by a direct call in `tests/unit/cli/recall-benchmark.test.ts` (fixture-response mode) — never by running the full campaign, which would make the disposition depend on the model rather than on the scan. Each row is written to fail if the scan's disposition is wrong, not merely if it throws.

| # | Input (shape) | Expected | Why it is an edge case |
| --- | --- | --- | --- |
| P1 | A bare `sk-` prefix with no body, at end of line | no match | Boundary-character variant: the minimal truncated form. A pattern anchored only on the prefix must not fire when no token body follows |
| P2 | Uppercase/mixed-case `SK-`, `Bearer`/`bearer`/`BEARER` | match | Boundary-character variant: credential vocabulary is case-insensitive in the wild; a case-sensitive pattern is silently blind |
| P3 | A shape preceded/followed by word characters with no separator (`xxsk-…yy`, `sk-…suffix`) | per-shape, asserted | Boundary-character variant: whether the scan requires a token boundary. The disposition is asserted per shape rather than left to an accidental `\b` |
| P4 | Padded with surrounding whitespace, tabs, and a trailing `\r` | match or no match per row | Boundary-character variant: a line ending in CRLF must not shift the reported line/column |
| P5 | A quote- or fence-delimited occurrence inside JSON, markdown prose, and a code fence | match | Boundary-character variant: the same value inside a JSON string, inside prose, and inside a fenced block — the scan reads raw text, so all three must be treated alike |
| P6 | `sk-` appears in ordinary prose unrelated to credentials (`sk-` as an abbreviation, `risk-`, `task-`) | no match | Boundary-character variant: prefix collides with common English substrings |
| P7 | A **negative** case: the fixed non-authenticating placeholders the test's allowlist names (`sk-canary000000000000000000000000000000`, `<the recorded basis>`, `<token>`), each of which is credential-*shaped* but authenticates nothing | no match, **or** a match the allowlist check accepts as a source-controlled non-authenticating placeholder | Negative case (strings that resemble matches but must not be treated as a leak) — the case that stops the scan from failing the tree it is meant to certify. | P8 | A negative case: `authorization: "<not set>"`, `token: null`, `password: ""` — key-named fields carrying placeholder/empty values | no match | Negative case: the key-named rule fires only on a *non-placeholder* value, so empty sentinels must not |
| P9 | Two credential values on one line (`Bearer a… and Bearer b…`, or `ghp_…` then `sk-…`) | two matches, both reported with their line | Multiple occurrences on one line: a scan that returns only the first occurrence under-reports |
| P10 | The same value repeated on several lines | one match per line | Multiple occurrences across lines: reported lines name each site |
| P11 | A JWT and a `Bearer` wrapping a JWT on one line | both shapes reported | Nested/overlapping constructs: the inner token is not consumed by the outer pattern |
| P12 | A value split across a line break (`sk-\n…`) or broken by markdown emphasis (`sk-**…**`) | no match | Nested/overlapping constructs: the scan reads text as-is; a broken token is not a credential, and the case pins that the scan does not silently join lines |

### Concurrent-event-source addendum

This plan **is** concurrent-event-source-bearing, and the classification is not the whole file: the sweep's own pass step (rule 3) is synchronous and adds no listener, timer, or queue — the sweep does not make a second model call and does not add a scheduler. The block applies because of **step 11's benchmark driver** (plan L254–L266), which the plan itself already describes in concurrent terms, so "not applicable" would contradict the plan's own text. The protocol's classification signals are met on all three counts: **(a) timers that can execute concurrently** — `--runs n` repeats `main`'s work in a loop and the plan moves the `AbortController`/`passTimeoutMs` timer inside that loop (`src/cli/recall-benchmark.ts:447-449` builds one controller and one timer for a whole invocation today), so a timer is created and cleared once per run with a live `unref` between them; **(b) shared mutable state multiple execution contexts read or write** — the campaign's run-record array is written per iteration, and the precision runs share **one** `model` client across a `Promise.all` (`src/cli/recall-benchmark.ts:475-489`), which the plan names as the `reportedModel` race site (L264) and the cross-attribution defect (L266); **(c) teardown sequences that race with incoming events** — each run's timer must be cleared before the next run's is created, and the `unref` must not let a completed run's timer hold the process or fire into a later run. The seven checklist items follow, each a design decision or an explicit not-applicable with rationale. The section governs **implementation step 11** and substantiates **AC8, AC9, AC11** (each run's own recorded identity and cost figures, and the same-configuration pairing), matching the parser-risk addendum's own AC-tagged pattern. **AC8, AC9, AC11**

**1. Shared mutable state guards.** The campaign's run-record array is the only cross-run mutable structure, and it is written **only by the sequential loop body** — one iteration at a time, each appending at its own `runIndex`, with no await-time interleaving between two iterations because the loop awaits each run before starting the next. That is why the array position is a stable identity (the failure-record shape at L256 relies on it): no two iterations can write the same index concurrently. The **shared `model` client is the one genuinely shared object across concurrent execution**, and the plan's answer is to make the shared object stateless with respect to per-request results: `reportedModel` travels on the per-response `ModelCompletion` (`model-client.ts` entry, L71) and never on the client, because a client-level "most recent value" read by the precision `Promise.all` would attribute whichever concurrent call resolved last to every fixture record. That is a design decision, not a guard on the client — the client is left safe to share by construction rather than by a mutex.

**2. Re-entrancy / in-flight tracking.** Not applicable — there is no re-entrant entry point. `main` is invoked once per process, `--runs n` is a **sequential** `for` loop (the plan says "repeat the benchmark `n` times, emitting one record per run", not "in parallel"), and no run's inference is started before the prior run's `await` settles. The single concurrency point in the whole change is the precision `Promise.all` over fixtures within **one** run, and those fixtures are independent, write to their own records, and share no mutable state (item 1). No in-flight set, generation counter, or ENOENT-style guard is needed because no second execution context can enter a run body while one is in flight; adding one would be an unrequested abstraction.

**3. Event deduplication.** Not applicable — the benchmark's events are the run records it appends itself and the `sweep_pass_record` progress line it emits per sweep-on run; both are emitted exactly once per run by the single sequential loop, and neither is driven by an external event stream that could redeliver. There is no webhook, no listener, and no at-least-once source in this path, so there is nothing to dedupe.

**4. Listener and resource cleanup.** The `AbortController`/timer pair is the resource, and the plan moves it inside the per-run loop: **created before that run's inference and cleared on that run's completion** (L256), so `--runs 5` no longer shares one deadline (the defect L256 names — a shared timer aborts every remaining run once the aggregate invocation passes one `passTimeoutMs`). The `unref()` is preserved on each per-run timer, so a completed run's timer never holds the process open and a campaign's exit is not delayed by an already-finished run's deadline. Fixture-response mode (the mode every unit test runs in) opens no network resource at all.

**5. Race conditions at initialization.** The per-run `fixture` and `configuration` blocks are **resolved before that run's inference** (L256), so they exist even for a run that throws — which is what lets a failure record carry them and what makes the failure-record shape (item 7) derivable. There is no initialization window in which a run's identity is half-built while another reads it, because the next run does not begin until the prior run's record (success or failure) is appended.

**6. Race conditions at teardown.** Sequencing, not races: the loop body appends the run's record **and** clears that run's timer before the next iteration constructs its own, so a run's timer cannot fire into a later run's inference and a later run cannot observe a prior run's aborted signal. The plan's exit rule — the array is written to `--output-file`/stdout **before** the process exits, including when the campaign holds failure records (L256) — makes the teardown order explicit: write the file, then exit, so a mid-campaign failure cannot lose the partial array to an early exit.

**7. Error propagation across async boundaries.** This is the item the plan's record-and-continue policy exists for (L256): each iteration runs inside its own `try`/`catch` that converts a thrown per-run error into a **failure record** at that run's array position rather than letting it escape `main` — today the inference call is unguarded, so a throw on run 3 kills the process and discards runs 1–2. The failure record carries `runIndex`, `fixture`, `configuration`, and a `failure` block with a stage `reason`, a **redacted** `message` (the same `redactForbiddenValues` treatment the CLI already applies, because model/GitHub error text is the shared-state content that must not carry a credential), and an `aborted` flag that distinguishes the `passTimeoutMs` abort from an ordinary error. A run whose deadline passed is bounded by that deadline, not by the client: its body is raced against the deadline, its signal is aborted, and it is then waited on for a bounded grace period so the next run does not overlap a request that settles on abort. A request still in flight after the grace period is recorded with `unsettledAfterDeadline: true` rather than holding the campaign, and the campaign stops there: it starts no further run while a request may still be in flight, so its records exist only up to that run and its exit code is non-zero. A resumed run checks its signal after each stage that awaits the client so it starts nothing further. Errors therefore propagate **into the record**, not across the loop boundary, and the campaign's exit code is non-zero when any run failed, so a partially-failed campaign is distinguishable from a clean one by exit code alone. On the **pass** side (rule 4), the same principle already governs: a terminal failure after review execution is classified on the `classified` flag rather than propagated as an unhandled rejection, and the sweeping step is synchronous so it introduces no new async boundary for an error to cross.

**Conditional item — new concurrent patterns.** The plan introduces **one** new concurrent pattern, and it is named rather than incidental: the precision `Promise.all` over one shared client (L264/L266). Its design decision is recorded in item 1 — the shared client carries no per-request result, and the per-response `reportedModel` is what each fixture records — and its verification is the scenario-6 test that drives two concurrent fixtures returning different reported identities and asserts no cross-attribution (L266). No other concurrent pattern is added: the campaign is sequential, the pass is synchronous, and no listener, queue, or background task is introduced.

This is why the new fields are unconditional: they cannot break the single-run contract precisely because that contract is a named-field read, not a closed shape. `--runs n` with `n > 1` writes the `n` run records as a JSON array to the same `--output-file` — the array is only ever produced where the caller asked for repetition, so no existing single-run consumer can be handed one by default. **Each iteration constructs and disposes its own `AbortController`/`passTimeoutMs` timer** — today `main` builds one controller and one timer for the whole invocation (`src/cli/recall-benchmark.ts:447-449`: `const controller = new AbortController(); const timeout = setTimeout(() => controller.abort(), config.passTimeoutMs)`), so `--runs 5` would abort every remaining run once the aggregate invocation passed one `passTimeoutMs`, silently truncating the campaign into partial records while the run count still read 5. The timer moves inside the per-run loop (created before that run's inference, cleared on its completion, and its `unref` preserved), so `passTimeoutMs` keeps its one meaning — one pass's deadline — under repetition, and an aborted run is one failed run the campaign records rather than a fixture-wide cutoff. **A run that fails is recorded, not discarded, and the campaign continues to the next run.** Today the inference call is unguarded — `main` has no per-run `try`/`catch`, so a model error propagates out of `main`, the process dies, and a `--runs 5` invocation that fails on run 3 writes nothing at all, silently dropping runs 1–2 and contradicting the runbook's troubleshooting rule to "record the partial results with timestamps and the failure reason; never silently drop attempted runs from the evidence" (`docs/testing/ronda/105-category-forced-review-sweep.smoke-test.md`). Each iteration therefore runs inside its own `try`/`catch` that converts a thrown per-run error into a **failure record** rather than letting it escape the loop. The failure record is a distinct shape on the same array position as a successful run: it carries `runIndex`, the same `fixture` and `configuration` blocks a successful run carries (resolved before the run's inference, so they are available even when the run fails), and a `failure` block — `{ reason: string; message: string; aborted: boolean }`, where `reason` names the failing stage (`model`, `github`, `timeout`, `unknown`), `message` is the thrown error's message **passed through the runner's existing redaction before it is written** (the values on this path are model/GitHub error text, so the same `redactForbiddenValues` treatment the CLI already applies to found/missed/false-positive output must cover it, per AC13/AC14's no-credential rule), and `aborted` distinguishes the `passTimeoutMs` abort from an ordinary error. A failure record carries **no** recall/found/missed/precision/`originalThirteenSubset`/per-category/cost fields, so a consumer can tell the two shapes apart by the `failure` block's presence alone and a failed run is never miscounted as a run that found nothing. The campaign keeps looping after a failure record, so the array always holds one entry per attempted run — `n` entries for `--runs n` whenever each attempt reached the loop body, whether it succeeded or failed — which is exactly what makes the partial evidence complete rather than truncated. **Exit and output behavior**: the array (with its failure records) is still written to `--output-file`/stdout before the process exits, so the partial campaign is on disk; the process exit code is non-zero when any run in the campaign failed (the existing pass/fail gate already returns `1`, and a campaign with a failure record returns `1` regardless of the surviving runs' recall, so a failed campaign cannot be mistaken for a clean one by an exit-code check), while a campaign whose every run is recorded as a successful run keeps the current `found ≥ 6 && !missed.includes("sensitive-value-exposure") && falsePositives.length === 0` gate unchanged. This is deliberately a record-and-continue policy, not a fail-fast one, because the campaign's purpose is measurement over a real model endpoint where a transient failure is expected and the surviving runs remain evidence.
