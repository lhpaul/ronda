## Summary

**Approach**: Record the architecture amendment first (in **both** `docs/project/3-software-architecture.md` and `docs/constitution.md` — see **Spec amendment carried by this plan PR**), then add repository context as a bounded, in-pass phase of `runReviewPass` that mirrors the two-phase shape `select-authoritative-docs.ts` already uses: identify candidates from the changed lines, resolve them at the reviewed head, apply budgets, attach a labelled untrusted prompt section, record the outcome. Since the owner's amendment of 2026-09-29 there is **one candidate kind** — the definitions the changed lines depend on — so no reverse-reference scan of the repository exists anywhere in this plan. Reads go through the **existing** GitHub contents seam (`GithubOperations.readFileAtRef`, backed by `src/github/repo-content-reader.ts`) plus one new recursive git-tree read — **no checkout, no working area, no `git` subprocess, no filesystem write** (plan decision **D1**). References are bound with the **TypeScript compiler API in-process** over the in-memory file set the reads produced (plan decision **D2**), so a candidate is the declaration the reviewed language's own checker binds to and an unbindable reference is dropped as `ambiguous_resolution` rather than guessed. Enablement and the three budgets ride the operator-configuration precedence the `#105` sweep switch already established. This repository's own value is supplied as a **repository variable** and is set on only after the AC4, AC5 and AC23 evidence is committed.

**Estimated complexity**: L

**Rationale**: The wiring is medium (one config group, one selection module, one resolver module, one prompt section, two renderers, one fork gate, one non-publishing control-pass entrypoint), but the item's bulk is correctness and evidence: a compiler-accurate resolver with a 100%-precision bar on a recorded fixture (AC23), a hostile-head read-only demonstration with structural and observational parts labelled apart (AC4, AC5), a paired interleaved recall/precision/cost campaign under one immutable model version (AC13–AC16), an evidence-tier ledger (AC17), and an ordering rule that gates this repository's switch on the evidence commits (AC19).

**Dependencies**: None blocking. The spec names #105 (merged — the three target seeds `api-evidence-state-reconstruction`, `external-output-parsing-lossy`, `guard-fails-open` exist in `tests/fixtures/recall-benchmark/manifest.json`), #53 and #55 (merged) as evidence and surface lineage. #127 is a documentation follow-up and is **not** touched here. If the three seeds are absent from `manifest.json` when implementation begins, step 13 stops and raises it rather than reconstructing seeds.

| **D1** | **Read mechanism: GitHub API reads, in memory. No checkout, no working area, no `git` subprocess, no filesystem write for reviewed content.** One recursive git-tree read at the reviewed head, used **only** to resolve module specifiers to concrete paths (`GET /repos/{o}/{r}/git/trees/{sha}?recursive=1`), then per-file text through the existing `readFileAtRef` contents seam for the changed files and their import closure. | The amendment leaves the mechanism open and the guarantees are written over the *reads*, so the cheapest mechanism that makes the guarantees **structural** wins. (a) AC4's three read-side attacks cannot arise: nothing is materialised on a filesystem, so no `.gitattributes` filter or driver has anything to act on; a symlink and a submodule are tree/contents entries the existing reader refuses before decoding (Verification Log), never paths something follows. (b) AC9's "no repository other than the reviewed head's own" is enforced at one seam bound to `(owner, repo, headSha)`. (c) AC12 becomes vacuous **on both ingresses**: no working area is ever created, so nothing can outlive a pass, be shared between passes, or need removing on any of the five settlement paths — which removes the largest risk the long-lived webhook process would otherwise take on. (d) No new token scope and no second git identity — the two costs the decision being amended cited as its reason. The tradeoff is HTTP round trips instead of one fetch; bounded by D3's time budget and, since the owner removed call sites, confined to the changed files and their import closure rather than the whole source set. A shallow fetch was rejected because it re-acquires exactly the materialisation surface (a), (b) and (c) are free of, and would have to buy each of them back with hardened `git` invocation flags and a cleanup path on five settlement paths. **Consequence for Operational Visibility**: because no working area exists, the pass emits **no** cleanup-completion log line and the cleanup-failure business rule can never fire. | **D5** | **The requested set is deterministic; the resolved set is a deterministic *prefix* of it, truncated by the time budget.** Candidate **identification** — reading the changed TypeScript/JavaScript files at the head and listing their references and defined symbols — is bounded by the **pass deadline**, never by the context time budget, so a context-budget expiry can never erase or alter the requested set. Candidate **resolution** proceeds in the deterministic **read (discovery) order** defined in the resolver bullet — not in the priority key order, which cannot govern the reads because a candidate's own location is unknown before its declaring file is read — under the context time budget; on exhaustion the pass **keeps every candidate it has already resolved** and drops the remainder with the reason `time_budget`. The count and character budgets are then applied to the resolved candidates in the **Context Selection Order** key order. A changed source file is **accounted for** when its read succeeded, its content type was refused, it was absent, or it failed to parse — all four being deterministic facts about the head — and **unaccounted** only when its read failed transiently after the existing bounded retry; a pass with any unaccounted changed file records its path and can never record `nothing_to_resolve`, which would falsely claim the changed lines named nothing. Where the **pass** deadline itself expires during identification, the pass never issues its review request and therefore owes no repository-context record at all, exactly as the sweep record behaves on that path. | AC8 and AC20 appeared to pull in opposite directions, and the **repository owner decided it on 2026-09-29**: keep the resolved prefix. The spec now carries the clarifying clause (AC20 and **Context Selection Order** → Reproducibility: reproducibility is over the candidate set and the selection order; which candidates survive a time-budget cutoff may vary, and the record lists every time-budget drop). The supporting reading is recorded here so the decision is not re-litigated. Three textual facts support it. (2) The spec's closed drop-reason list includes `time budget` as a **per-candidate** reason; a per-candidate reason is only meaningful if the budget can stop part-way, leaving some candidates resolved and others dropped. An all-or-nothing design would make that reason degenerate, so the spec's own vocabulary rules atomicity out. (3) AC20's reproducibility clause, read in the spec's **Context Selection Order → Reproducibility** paragraph where it is defined, is written over **the order**: "The order depends only on the reviewed head, the changed lines, and the configuration. Taken together: the order is absolutely deterministic, the retained set is always a **prefix** of that order rather than an arbitrary subset, and the record states the prefix and why it ended. That is the strongest guarantee compatible with both criteria. **Rejected alternative, recorded so it is not reintroduced**: making the phase atomic — discard everything on exhaustion — was drafted and rejected against facts (1) and (2), and the owner's decision of 2026-09-29 closed it. It buys absolute determinism of the retained set at the price of failing AC8's plain words and of making a spec-defined drop reason unreachable. Verified by the reproducibility test: the same head and configuration, run twice through the injected reader with different per-read latencies, produce identical requested sets and identical ordering, with any difference confined to the prefix length and fully explained by `time_budget` drops. | AC8, AC20; **Context Selection Order** → Priority, Reproducibility, Dropping |

- [ ] **Module-resolution contract (fixed this iteration, not inferred).** AC23's guarantee is only as good as the resolution it rests on, so the contract is specified here rather than left to the implementer:
  - **Two distinct orders, and they are not the same order.** The **Context Selection Order** keys cannot govern the reads, because a candidate's own location — priority keys 2 and 3 — is unknown until the declaring file has been read and the reference bound. The plan therefore fixes two orders. **Read (discovery) order**, deterministic from the head alone: a FIFO queue seeded with the changed source files in changed-file-path ascending order — those were already read in (a) and are **not** re-read; they seed the queue only so their specifiers are enumerated first — then, for each file dequeued, its module specifiers in **source order**, each resolved to a concrete path against the tree listing and appended if not already queued or read, deduplicated by path. This depends on nothing but the head and the changed lines, so two passes read in the same sequence and only *how far* they get can differ (D5). **Priority (selection) order**, the spec's three keys, is applied to the **resolved** candidates once binding is done, purely to decide which ones the count and character budgets retain — exactly what **Context Selection Order** → Dropping specifies.
  - **A requested candidate is identified by its reference; a resolved candidate additionally carries its declaration's location.** The requested set is therefore knowable from the changed files alone, before any closure read, and it is computed in (a) from a `ts.Program` built over the changed files by themselves: one requested candidate per **distinct referenced symbol**, deduplicated across the changed lines, so a symbol named on three changed lines is one candidate and not three (E6). A reference whose declaration is itself in the changed files is excluded, because the changed lines already show it (E8) — that exclusion is decidable from the changed-files-only program, which is why it belongs to (a). `candidatesRequested` is the size of that set. Priority key 1, changed-line position, is the **earliest** changed line that references the symbol and is known at request time; keys 2 and 3 become known only on resolution, which is why they order resolved candidates only.
  - **Every drop is fully identified, including a `time_budget` drop.** A reference whose declaring file was never read has no candidate location to record, so its `RepositoryContextDrop` carries the **reference's** identity instead — `symbolName`, plus the `path` and `line` of the changed line that names it — and never an empty or placeholder location. That satisfies the spec's identifier set (symbol name, file path, line number) for every drop reason, and makes AC20's "the pass record is sufficient to explain why a given candidate was or was not included" true for the time-budget case too.
  - **Compiler options are a fixed set, and the reviewed repository's `tsconfig.json` is not read this iteration**: `target: ES2022`, `module: Node16`, `moduleResolution: Node16`, `allowJs: true`, `checkJs: false`, `esModuleInterop: true`, `strict: false`, `noEmit: true`, `skipLibCheck: true`, `types: []`. The values mirror this repository's own `tsconfig.json` except `strict` and `checkJs`, which are relaxed because the resolver needs *binding*, not diagnostics, and a strict-mode error never changes which declaration a reference binds to. Reading the reviewed head's `tsconfig.json` is deferred (see the limitation below) because an inherited `extends` chain would need further reads and could not be resolved within the time budget deterministically.
  - **Specifier resolution order** against the inventory, applied in this order and stopping at the first hit: the literal path; then the TypeScript extension substitutions for a `.js`-family specifier (`.js` → `.ts`, `.mjs` → `.mts`, `.cjs` → `.cts`, `.jsx` → `.tsx`); then the extensionless forms `.ts`, `.tsx`, `.d.ts`, `.js`; then `<specifier>/index.<ext>` in that same extension order. The `.js` → `.ts` substitution is what makes this repository's own `Node16` import style — and the plan's `.js` re-export edge case E3 — resolve at all.
  - **A bare specifier** (one that does not start with `.` or `/`) is **not** resolved: no `node_modules` of the reviewed repository is read, which is what keeps the read set inside the reviewed head's own tracked content (AC9). A reference whose declaration would live in a bare-specifier module therefore binds to nothing and is dropped.
  - **`paths` / `baseUrl` aliases are unsupported** this iteration, a direct consequence of not reading `tsconfig.json`. An alias specifier is unresolvable, exactly like a bare specifier.
  - **Every unresolvable specifier is safe by construction, not by accident**: an unresolved module gives the reference zero bound declarations, which **Context Selection Order** already requires to be dropped with the reason `ambiguous_resolution` rather than guessed. No new drop reason is introduced and no fallback to textual matching exists — a textual fallback is exactly what D2 rejected.
  - **Tests**: `tests/unit/review/symbol-resolver.test.ts` gains one case per resolution rule above — a `.js`-specifier resolving to a `.ts` file, an extensionless specifier, a directory `index` specifier, a bare specifier, and a `paths`-alias specifier — with the last two asserting a drop rather than a guess.
  - **Unreadable and refused paths — one contract for both positions.** A **drop presupposes a candidate**, so the two positions a refused path can occupy are treated differently and the difference is stated here rather than left to the implementer: (a) as a **candidate target** — the file a depended-on declaration would live in — the candidate is requested and dropped `read_failed`; (b) as a **changed path** itself, the file yields no reference and therefore **no candidate and no drop**, because there is nothing to attribute a drop to. The same rule covers a changed file that fails to parse (E11) and one whose content read is refused as a non-`file` type (E12). Where (b) leaves zero candidates across every changed file **and every changed source file was accounted for** — read, content-type refused, absent, or unparseable, all deterministic facts about the head — the outcome is `nothing_to_resolve`: honest, because nothing was requested and so nothing failed. A changed source file whose read failed **transiently** is the one case that is *not* accounted for: it makes `nothing_to_resolve` unavailable as an outcome (D5), because the pass cannot honestly claim the changed lines named nothing, and its path is recorded in `unreadableChangedFilePaths`. D4 applies first: a changed path outside the TypeScript/JavaScript extensions never reaches either position.
  - **Recorded limitation**: repositories that rely on `paths` aliases or on bare-specifier declarations get fewer candidates, recorded as `ambiguous_resolution` drops. That is a recall limitation, never a precision one, which is the direction AC23 demands. Lifting it — reading the reviewed head's `tsconfig.json` and its `extends` chain — is a follow-up, not part of this item. **AC9, AC23**

## Testing Strategy

**Test types**: Unit, integration, demonstration (recorded evidence), smoke.

**Key scenarios to test**:

1. Selection order is total and stable: two candidates identical under each key in turn are ordered by the next key; the same input yields the same order every time. **And reproducible under timing variation**: the same head and configuration, run twice through the injected reader with **different per-read latencies**, produce an identical requested set, read it in an identical sequence, and order the resolved candidates identically; any difference is confined to how far the read got, and every shortfall carries a `time_budget` drop — AC20 as clarified by the owner on 2026-09-29, and D5.
2. Budgets drop whole candidates in reverse priority order; a single candidate exceeding the character budget is dropped, not truncated; every drop carries one of the five recorded reasons — AC6.
3. Outcome tests apply in the recorded order: pre-review-execution → `not_applicable` and no record; fork head with the switch on and every budget at its most permissive → `fork_excluded`, no record, no activation line, no budget figure; validly disabled → `off` and no record; enabled with zero candidates → `nothing_to_resolve`; all resolved → `used`; some → `partial`; at least one requested and none resolved → `unavailable` — AC3, AC10, AC19.
4. Switch resolution: blank at the higher source defers to the lower; both blank → off, nothing recorded; a recognized off value → off, nothing recorded; a non-blank unrecognized value at the higher source → off even with a recognized on value at the lower source, and the degraded record is emitted **only** on a same-repository pass that reached review execution, without the raw value — AC21.
5. Budget resolution: a non-numeric or non-positive value falls back to the recorded default and records the fallback; no source combination yields an unlimited budget — AC21.
6. The diff is byte-identical in the prompt with the feature off and with it on at every budget setting, and context characters never enter the `maxPatchChars` measurement — AC7.
7. A time budget forced low enough to expire before the **first** candidate resolves yields `unavailable`; one that expires part-way yields `partial`, retaining exactly the candidates resolved by then — the prefix of the deterministic **read** order — and dropping the remainder `time_budget`; both publish the review and neither extends the pass deadline nor raises the job backstop. A budget large enough for resolution to complete yields `used`, or `partial` when the count or character budget then drops candidates — AC8, D5.
8. Read failures are split by what failed, and each has its own expected outcome — AC11, AC3:
    - **Candidate-target reads denied** (the changed files read fine; every closure read throws or returns `undefined`): every requested candidate is dropped `read_failed` and the outcome is `unavailable`.
    - **A changed source file absent** (its read returns `undefined`, a 404): it is **accounted for** — absence is a deterministic fact about the head — contributes no reference, and does **not** populate `unreadableChangedFilePaths`; `nothing_to_resolve` stays available if no changed file produced a reference.
    - **A changed source file failing transiently** (throwing past the bounded retry): it is **unaccounted**, its path is recorded, and `nothing_to_resolve` is forbidden (scenario 14).
    In all three the review is still published and no read failure reaches the shared failure path.
9. No reviewed-repository read is attempted through any path but the injected `readFileAtRef` / `readTreeAtRef` seam, and neither the phase nor the resolver touches `node:fs` or spawns a process for reviewed content — AC4, AC9, AC12.
10. Repeated passes create no working area and leave nothing behind; a pass aborted mid-read publishes no second review for the head; **and the webhook ingress runs no more concurrent review jobs with repository context than without it** — asserted by driving two deliveries through `startWebhookServer` with the feature on and confirming the second is queued rather than started while the first is in flight, exactly as the pre-feature test asserts, since the phase adds no job dispatch and no listener — AC12 (the no-working-area half is D1's structural guarantee: no temp path is created at all).
11. The control pass publishes no review, no check run, and no comment, and a head that already carries a published review still has exactly one afterwards — AC22.
12. Resolution precision on the AC23 fixture is 100%: every resolved candidate matches `expected.json`, and the unbindable reference is dropped `ambiguous_resolution` — AC23.
13. Review body content: the summary carries exactly one repository-context line naming the outcome, and no count, identifier, drop reason, or budget figure appears anywhere in the body; the check-run output carries the full record and no excerpt body — AC3.
14. `nothing_to_resolve` integrity: it is recorded when every changed source file was accounted for — read, content-type refused, absent, or unparseable — and none produced a reference; a pass with any **transiently unreadable** changed source file records `used`, `partial` or `unavailable` instead, with that path in `unreadableChangedFilePaths`; and a context-time-budget expiry never changes the requested set, because identification runs under the pass deadline — AC3, AC8, AC20, D5.

### Parser-risk addendum

This plan is parser-risk: `src/review/symbol-resolver.ts` parses source text and binds references, and AC23 sets a 100%-precision bar, so wrong parsing produces confidently false evidence rather than a visible failure.

**Edge-case enumeration** — concrete inputs, each mapped to a test in `tests/unit/review/symbol-resolver.test.ts`:

| # | Input | Expected |
| --- | --- | --- |
| E1 | Two types each declaring a method `read(path)`; a changed line calls `a.read(p)` where `a` has the first type | Exactly the first type's declaration; the same-named method on the other type is never a candidate |
| E2 | A module-level `resolve` shadowed by a local `const resolve` inside the changed function | The local declaration, not the module-level one |
| E3 | `export { inner as outer } from "./inner.js"`; a changed line imports `outer` and calls it | The declaration in `inner.ts`, reached through the re-export |
| E4 | A changed line referencing a name declared in a file the time budget stopped before reading | Dropped `time_budget` — never bound to a same-named declaration in a file that *was* read |
| E5 | A reference whose symbol has two declarations (a declaration-merged interface, or an ambient plus a local declaration) | Dropped `ambiguous_resolution` — not the first, not both |
| E6 | Two references to different symbols on the same changed line, plus one reference appearing twice on that line | Two distinct candidates; the repeated reference contributes one candidate, not two |
| E7 | An identifier inside a string literal, a comment, or a template-literal text span that spells a changed symbol's name | No candidate — the identifier is not a reference (this is the negative case a text-based resolver would fail, and the direct evidence for D2) |
| E8 | A symbol declared *and* called within the same changed hunk | The definition is not attached as a candidate for its own declaration site — the changed lines already show it, so re-sending it would spend budget on the diff |
| E9 | One changed line depending on seven distinct symbols declared in other files, under a candidate count budget of 3 | Three candidates by the priority keys — candidate location, then symbol name, since all seven share the same changed-line position — and four drops recorded `candidate_count_budget` |
| E10 | A changed `.md`, `.json`, or `.yml` file only (D4) | No candidate, outcome `nothing_to_resolve`, never `unavailable` |
| E11 | A syntactically invalid changed file at the head (mid-edit head, or a partial file) | No reference is taken from that file, so it yields no candidate and no drop; the file counts as **accounted for**, because unparseability is a deterministic fact about the head, so `nothing_to_resolve` stays available; the resolver never throws out of the phase and the other changed files are unaffected |
| E12 | A symlink (mode `120000`, reported by the trees API as `type: "blob"`), a submodule gitlink (mode `160000`), or a directory (mode `040000`), in two positions: (a) as a **candidate target** — the file a depended-on declaration would live in; (b) as a **changed path** itself | (a) The candidate is requested and dropped `read_failed`. (b) No reference, therefore no candidate and no drop — and where that leaves zero candidates, the outcome is `nothing_to_resolve`, because nothing was requested. In both positions the entry is absent from the inventory — excluded by the mode allowlist, never by a `type` check — and independently refused by the content read, and nothing outside the reviewed repository is read |
| E13 | A `.d.ts`-only declaration for a symbol whose implementation is not in the read set | Bound to the `.d.ts` declaration when that is the single declaration; excerpt is that declaration |
| E14 | The three resolvable specifier forms from the module-resolution contract: a `.js` specifier whose target is a `.ts` file, an extensionless specifier, and a directory specifier resolving to `index.ts` | Each resolves to the intended file; a `.js`-specifier case is required because this repository's own `Node16` import style and E3's re-export both depend on it |
| E16 | One changed source file reads successfully and a second fails **transiently** (the injected reader throws past the bounded retry) | The first file's references become candidates; the second contributes none and is **unaccounted**; its path appears in `unreadableChangedFilePaths`; and the outcome is `used`, `partial` or `unavailable` by how many candidates resolved — **never** `nothing_to_resolve`, even when the first file produced no reference either. Contrast E11 and E12, whose failures are deterministic and therefore accounted for |
| E15 | The two unresolvable specifier forms: a bare specifier (no `./` or `/` prefix) and a `paths`-alias specifier | Both leave the reference with zero bound declarations, so it is dropped `ambiguous_resolution`; no `node_modules` read is attempted and no textual fallback runs |

**Suppression semantics**: not applicable — the feature recognizes no inline or directive suppressions. Whether a candidate is included is decided only by the selection order and the budgets.

### Concurrent-event-source addendum

**Not applicable.** Each of the three classifier signals is absent: (a) the feature adds no event listener, socket callback, timer, or async queue — the repository-context phase is a sequential `await` sequence inside the single existing review pass, under the pass deadline's `AbortSignal`; (b) it adds no mutable state shared across execution contexts — the file set, the candidate list, and the record are created and consumed inside one `runReviewPass` invocation and referenced by nothing outside it; (c) it adds no initialization or teardown sequence that could race with incoming events, because D1 creates no working area and the webhook ingress's existing one-active-review-job rule and bounded queue are untouched (AC12). The one abort path the phase adds — the time budget's signal — resolves inside the phase, which returns `partial` or `unavailable` rather than propagating.

## Residual verification strategy

This plan has a pattern-completeness obligation (every reference on a changed line must be resolved or explicitly dropped) and a numeric target (AC23's 100% precision). The evidence the implementation must produce before `ready-for-human-review`:

- **Resolution completeness**: for the AC23 fixture, the count of references identified, resolved, and dropped, with every drop carrying one of the five recorded reasons. The residual is the dropped set, and it is not a gap: an unbindable reference is *required* to be dropped. Evidence source: `docs/testing/ronda/repository-context-resolution-precision-106.md` and `tests/unit/review/symbol-resolver.test.ts`.
- **Precision**: resolved candidates that are correct over all resolved candidates on the AC23 fixture, which must be 100%. A lower figure is a defect that blocks step 15, not a residual to report. Evidence source: the same document.
- **Edge-case coverage**: E1–E16 each map to a named unit test, and scenarios 1–14 each map to at least one file in the Testing Strategy table with any two-file split named. The residual check is that the enumeration and the test files agree with no unmapped case in either direction. Evidence source: `tests/unit/review/symbol-resolver.test.ts` and the Testing Strategy table.
- **No-working-area claim**: the assertion is structural (D1 creates none) and is verified observationally by repeated passes leaving nothing behind and by the phase never touching `node:fs` for reviewed content. Evidence source: `tests/integration/core/review-pass-repository-context.test.ts` and the AC4 demonstration record.
- **Switch-ordering claim (AC19)**: the residual evidence is the ordering itself — the commit timestamps of the three evidence documents against the recorded time of the repository-variable change. Evidence source: `docs/testing/ronda/repository-context-effect-evidence-106.md`.
